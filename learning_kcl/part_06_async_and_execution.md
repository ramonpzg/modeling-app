# Part 6: Async Rust and KCL's Execution Model

KCL talks to a geometry engine over WebSockets. Operations like "extrude this sketch" are sent to the engine, which does the heavy computation and sends back results. This is inherently asynchronous. While waiting for the engine, KCL can do other work.

Python has `async`/`await`. Rust has `async`/`await`. They look similar but work completely differently. Python's is runtime-based (event loop). Rust's is compile-time transformation with zero-cost abstractions. Let's understand how it works and how KCL uses it.

## Async in Python: A Quick Refresher

```python
import asyncio

async def fetch_data(id):
    await asyncio.sleep(1)  # Simulate network delay
    return f"Data for {id}"

async def main():
    result = await fetch_data(42)
    print(result)

asyncio.run(main())
```

When you `await`, the event loop suspends the coroutine and runs other tasks. When the awaited operation completes, the coroutine resumes. The event loop is part of Python's runtime.

## Async in Rust: Futures

```rust
use tokio::time::{sleep, Duration};

async fn fetch_data(id: u32) -> String {
    sleep(Duration::from_secs(1)).await;
    format!("Data for {}", id)
}

#[tokio::main]
async fn main() {
    let result = fetch_data(42).await;
    println!("{}", result);
}
```

Looks similar. But Rust's `async` is a compile-time transformation. An `async fn` returns a `Future`, which is a state machine generated by the compiler. The `tokio::main` macro sets up the runtime that polls futures.

The key difference: Python's async is built into the language. Rust's async is a library feature. You can choose your runtime (tokio, async-std, smol, etc.) or write your own.

## Futures: State Machines

When you write:

```rust
async fn example() {
    println!("Start");
    sleep(Duration::from_secs(1)).await;
    println!("Middle");
    sleep(Duration::from_secs(1)).await;
    println!("End");
}
```

The compiler generates something like:

```rust
enum ExampleFuture {
    Start,
    FirstSleep(/* sleep future */),
    Middle,
    SecondSleep(/* sleep future */),
    Done,
}

impl Future for ExampleFuture {
    type Output = ();

    fn poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<()> {
        match self {
            Start => {
                println!("Start");
                // Transition to FirstSleep state
            }
            FirstSleep(sleep_future) => {
                // Poll the sleep future
                // If not ready, return Pending
                // If ready, transition to Middle state
            }
            // ... and so on
        }
    }
}
```

Each `.await` is a suspension point. The state machine tracks which point you're at. When you poll the future, it executes until the next `.await`, then returns `Pending` or `Ready`.

This is zero-cost. No heap allocation for the coroutine (unless you explicitly box it). No runtime overhead beyond what you write.

## The Future Trait

```rust
pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}
```

A future is something that produces a value `Output` eventually. You poll it repeatedly until it's ready. If it's pending, you wait and poll again later.

The runtime (tokio, async-std, etc.) manages the polling. When a future is pending, it registers a waker with the context. The waker notifies the runtime when the future is ready to make progress (e.g., when network data arrives).

## Pin: The Confusing Part

Notice `Pin<&mut Self>` in the poll signature? That's Rust's way of saying "this value cannot be moved in memory."

Why does this matter? Imagine a future that holds a pointer to itself:

```rust
struct SelfReferential {
    data: String,
    pointer: *const String,  // Points to data
}
```

If you move this struct, the pointer becomes invalid. `Pin` prevents moves. It guarantees the future stays at the same memory address while being polled.

Most of the time, you don't think about pinning. You just write `async fn` and `.await`. The compiler handles it. But when you use `Box::pin` or see `Pin<Box<Future>>`, that's why.

KCL uses `Box::pin` extensively because standard library functions return futures, and those futures need to be stored and polled by the executor.

## How KCL Uses Async

Look at a KCL stdlib function in `rust/kcl-lib/src/std/shapes.rs`:

```rust
pub async fn circle(
    args: Args,
    exec_state: &mut ExecState,
) -> Result<KclValue, KclError> {
    // Parse arguments
    let center = args.get_number_array("center", exec_state)?;
    let radius = args.get_number("radius", exec_state)?;

    // Send command to engine
    let response = exec_state
        .engine_connection
        .send_modeling_cmd(ModelingCmd::Circle {
            center,
            radius,
        })
        .await?;

    // Process response
    Ok(KclValue::Sketch {
        id: response.id,
        // ... more fields
    })
}
```

The `.await?` sends a command to the geometry engine and waits for the response. While waiting, other KCL code can run (if there are multiple async operations).

In Python, this would be:

```python
async def circle(args, exec_state):
    center = args.get_number_array("center")
    radius = args.get_number("radius")

    response = await exec_state.engine_connection.send_modeling_cmd({
        "type": "Circle",
        "center": center,
        "radius": radius,
    })

    return {"type": "Sketch", "id": response["id"]}
```

Similar code, but Rust's version is type-checked (the command must be a valid `ModelingCmd`, the response must match the expected type) and zero-cost (no runtime overhead).

## The Executor: Running Async Code

KCL's executor is in `rust/kcl-lib/src/execution/mod.rs`:

```rust
pub struct ExecState {
    pub memory: Memory,
    pub engine_connection: Box<dyn EngineConnection>,
    // ... more fields
}

impl ExecState {
    pub async fn execute_program(&mut self, program: &Program) -> Result<KclValue, KclError> {
        for item in &program.body {
            self.execute_body_item(item).await?;
        }
        Ok(KclValue::KclNone)
    }

    async fn execute_body_item(&mut self, item: &BodyItem) -> Result<(), KclError> {
        match item {
            BodyItem::VariableDeclaration(decl) => {
                let value = self.execute_expr(&decl.init).await?;
                self.memory.set(&decl.id.name, value);
                Ok(())
            }
            BodyItem::ExpressionStatement(expr) => {
                self.execute_expr(expr).await?;
                Ok(())
            }
            // ... more cases
        }
    }

    async fn execute_expr(&mut self, expr: &Expr) -> Result<KclValue, KclError> {
        match expr {
            Expr::Literal(lit) => Ok(self.literal_to_value(lit)),
            Expr::Name(name) => self.memory.get(&name.name).cloned()
                .ok_or_else(|| KclError::undefined_variable(&name.name)),
            Expr::CallExpressionKw(call) => {
                self.execute_call(call).await
            }
            // ... more cases
        }
    }
}
```

Each function is `async` and can `.await` on engine operations. The executor walks the AST, evaluates expressions, and sends commands to the engine as needed.

## The Box::pin Pattern

Standard library functions return `Pin<Box<dyn Future>>`:

```rust
type StdLibFn = fn(Args, &mut ExecState) -> Pin<Box<dyn Future<Output = Result<KclValue, KclError>>>>;
```

This is necessary because:
1. Different functions return different future types
2. We need to store them in a collection (dynamic dispatch)
3. Futures can't be moved (pinning)

The pattern:

```rust
pub fn circle(args: Args, exec_state: &mut ExecState) -> Pin<Box<dyn Future<Output = Result<KclValue, KclError>>>> {
    Box::pin(async move {
        // Implementation here
    })
}
```

`Box::pin` allocates the future on the heap and pins it. `async move` creates an async block that takes ownership of its captures.

In Python, you'd just return a coroutine:

```python
async def circle(args, exec_state):
    # Implementation
    pass

# Returns a coroutine object (similar to Future)
```

No boxing, no pinning. But also no compile-time type checking and no zero-cost abstraction.

## Send and Sync: Thread Safety

Rust futures can be `Send` (safe to send between threads) and `Sync` (safe to share between threads). This matters for async runtimes that use thread pools.

```rust
async fn example() {
    // This future is Send if all values it captures are Send
}

fn spawn_task<F>(future: F)
where
    F: Future + Send + 'static,
{
    tokio::spawn(future);
}
```

`tokio::spawn` requires `Send` because the future might run on any thread in the pool. If your future captures a non-Send value (like `Rc<T>`), it won't compile.

KCL's futures are `Send` because `ExecState` and all KCL values are `Send`. This allows parallel execution of multiple KCL programs.

## Concurrent Execution: Running Multiple Operations

KCL can run multiple async operations concurrently:

```rust
use tokio::join;

async fn create_two_shapes(exec_state: &mut ExecState) -> Result<(KclValue, KclValue), KclError> {
    let circle_future = circle(args1, exec_state);
    let rectangle_future = rectangle(args2, exec_state);

    let (circle, rectangle) = join!(circle_future, rectangle_future);

    Ok((circle?, rectangle?))
}
```

`join!` runs both futures concurrently and waits for both to complete. If the engine supports it, both operations happen in parallel.

In Python:

```python
async def create_two_shapes(exec_state):
    circle, rectangle = await asyncio.gather(
        circle(args1, exec_state),
        rectangle(args2, exec_state),
    )
    return circle, rectangle
```

Similar idea, but Rust's version is type-checked (you can't accidentally mix incompatible futures).

## The Engine Connection: Abstraction Over Transport

KCL abstracts the engine connection with a trait:

```rust
#[async_trait]
pub trait EngineConnection: Send + Sync {
    async fn send_modeling_cmd(&self, cmd: ModelingCmd) -> Result<EngineResponse, EngineError>;
}
```

There are multiple implementations:
- `WebSocketConnection`: Real connection to the engine
- `MockConnection`: For testing
- `WasmConnection`: For browser-based execution

The executor doesn't care which implementation it uses. It just calls `send_modeling_cmd` and awaits the result.

The `#[async_trait]` macro is necessary because Rust doesn't natively support async trait methods (yet). It desugars to:

```rust
pub trait EngineConnection: Send + Sync {
    fn send_modeling_cmd(&self, cmd: ModelingCmd)
        -> Pin<Box<dyn Future<Output = Result<EngineResponse, EngineError>> + Send + '_>>;
}
```

This is the `Box::pin` pattern again.

## Building an Async Evaluator

Let's build a simple async evaluator for our mini-KCL:

```rust
use tokio::time::{sleep, Duration};

struct AsyncExecState {
    variables: HashMap<String, Value>,
}

impl AsyncExecState {
    async fn execute(&mut self, program: &Program) -> Result<(), EvalError> {
        for stmt in &program.statements {
            self.execute_stmt(stmt).await?;
        }
        Ok(())
    }

    async fn execute_stmt(&mut self, stmt: &Stmt) -> Result<(), EvalError> {
        match stmt {
            Stmt::VarDecl(decl) => {
                let value = self.evaluate_expr(&decl.value).await?;
                self.variables.insert(decl.name.clone(), value);
                Ok(())
            }
            Stmt::Expr(expr) => {
                self.evaluate_expr(expr).await?;
                Ok(())
            }
        }
    }

    async fn evaluate_expr(&self, expr: &Expr) -> Result<Value, EvalError> {
        match expr {
            Expr::Number(n) => Ok(Value::Number(*n)),
            Expr::Name(name) => {
                self.variables
                    .get(name)
                    .cloned()
                    .ok_or_else(|| EvalError::UndefinedVariable {
                        name: name.clone(),
                        position: 0,
                    })
            }
            Expr::Binary { left, op, right } => {
                // Evaluate left and right concurrently
                let (left_val, right_val) = tokio::join!(
                    self.evaluate_expr(left),
                    self.evaluate_expr(right)
                );

                let left_val = left_val?;
                let right_val = right_val?;

                // Apply operator
                self.apply_binary_op(&left_val, op, &right_val)
            }
            Expr::Call { name, args } => {
                // Simulate async function call (e.g., to geometry engine)
                sleep(Duration::from_millis(100)).await;
                Ok(Value::Number(42.0))
            }
        }
    }

    fn apply_binary_op(&self, left: &Value, op: &BinOp, right: &Value) -> Result<Value, EvalError> {
        match (left, op, right) {
            (Value::Number(a), BinOp::Add, Value::Number(b)) => Ok(Value::Number(a + b)),
            (Value::Number(a), BinOp::Sub, Value::Number(b)) => Ok(Value::Number(a - b)),
            (Value::Number(a), BinOp::Mul, Value::Number(b)) => Ok(Value::Number(a * b)),
            (Value::Number(a), BinOp::Div, Value::Number(b)) => {
                if *b == 0.0 {
                    Err(EvalError::DivisionByZero { position: 0 })
                } else {
                    Ok(Value::Number(a / b))
                }
            }
        }
    }
}

#[tokio::main]
async fn main() -> Result<(), EvalError> {
    let program = parse("x = 10; y = x + 5; z = y * 2")?;
    let mut exec = AsyncExecState {
        variables: HashMap::new(),
    };

    exec.execute(&program).await?;

    println!("Variables: {:?}", exec.variables);
    Ok(())
}
```

This evaluator runs asynchronously. Binary expression operands are evaluated concurrently. Function calls simulate async operations.

## Structured Concurrency: Scoped Tasks

Tokio provides scoped tasks for structured concurrency:

```rust
use tokio::task;

async fn parallel_evaluation(exprs: Vec<Expr>, exec: &AsyncExecState) -> Result<Vec<Value>, EvalError> {
    let mut results = Vec::new();

    for expr in exprs {
        let result = exec.evaluate_expr(&expr).await?;
        results.push(result);
    }

    Ok(results)
}
```

You can also use `futures::future::join_all` for dynamic collections:

```rust
use futures::future::join_all;

async fn parallel_evaluation(exprs: Vec<Expr>, exec: &AsyncExecState) -> Result<Vec<Value>, EvalError> {
    let futures = exprs.iter()
        .map(|expr| exec.evaluate_expr(expr));

    let results = join_all(futures).await;

    results.into_iter().collect()
}
```

This evaluates all expressions concurrently and collects results.

## What You Just Learned

1. Rust's `async`/`await` is a compile-time transformation to state machines
2. Futures are polled by a runtime (tokio, async-std, etc.)
3. `Pin` prevents moving futures that reference themselves
4. `Box::pin` is used for dynamic dispatch with futures
5. `Send` and `Sync` traits ensure thread safety for concurrent futures
6. KCL uses async for engine communication
7. The `#[async_trait]` macro enables async trait methods
8. Concurrent operations use `join!`, `join_all`, or manual task spawning
